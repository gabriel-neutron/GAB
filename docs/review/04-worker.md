1. **The layout and reconcile workers claim a document's ingestion job and use it up on work that has no relation to that document.**

2. **A job that succeeds never gets an end state, so it stays `running` and the lease runs it again with no limit.**

4. **If `fail_job` throws, its error replaces the original fault, and the original fault is lost.**
   - file: `packages/worker/src/run-once.ts`:61
   - severity: minor
   - review agent's proof: `await on.query(FAIL, [job.id, reason]);` is inside the `catch`, and nothing guards it. So `throw fault` does not run when this call rejects. Trigger 1: the original fault is a lost connection (for example, `Connection terminated unexpectedly` during `runLayout`). The FAIL query then rejects with a client-closed error. The caller sees the second error, and the job is not marked failed. Trigger 2: the row is no longer `running` (for example, the lease released it). `fail_job` raises `job % is not running, and only a running job fails`, and this message hides the real failure. Wrap the `fail_job` call in its own try, and always rethrow the original `fault`.
   - verify agent's proof: In packages/worker/src/run-once.ts, lines 57-64, the catch block is:
```
} catch (fault) {
  if (job.attempt >= JOB_RETRY_LIMIT) {
    const reason = ...;
    await on.query(FAIL, [job.id, reason]);   // line 61
  }
  throw fault;                                 // line 63
}
```
No try guards the `await` on line 61. If the query rejects, the rejection leaves the catch block and line 63 does not run. The caller then gets the fail_job error and not the original fault. This is contrary to the doc comment on lines 42-44: "the failure still reaches the caller".

There are two real paths that make line 61 reject:
(1) db/apply/40_functions.sql lines 525-530. fail_job updates only `WHERE id = p_id AND status = 'running'`. If no row matches, it runs `RAISE EXCEPTION 'job % is not running, and only a running job fails'`. The comment on lines 17-18 of run-once.ts says that the lease returns a running row to the queue. release_expired_claims is granted to gabriel_app, so another process can release the row while a long run is in progress. On the last attempt, the FAIL call then raises, and that message replaces the real fault.
(2) packages/worker/src/main.ts lines 15-18 give runOnce one `pg.Client`, not a pool. If that connection breaks during runLayout or reconcileCorpus, the FAIL query goes to the same dead client and rejects. The caller then sees a client error, and the job stays running.
The test at run-once.test.ts:107-117 checks only the case where FAIL succeeds (the fake returns `[]`), so no test covers this. The defect is real. It is minor: diagnostics are lost, and the lease still recovers the row.

5. **The layout reads have no ORDER BY, so the same corpus can give a different picture, which breaks the layout's determinism.**
   - file: `packages/worker/src/layout-job.ts`:9
   - severity: minor
   - review agent's proof: `const ENTITIES = 'SELECT id FROM public.entities'` and the `LINKS` query have no `ORDER BY`. `entityLayout` depends on the input order in these places: the spiral seed (`reach: extent * Math.sqrt(index / count), angle: index * GOLDEN_ANGLE`), the tie-break between components (`numberAt(one, 0) - numberAt(two, 0)`), and the order of neighbours and edges, which changes the floating-point sums. PostgreSQL returns heap order, and heap order changes after an UPDATE of a row (for example, the rename act in a39e956) or after VACUUM. Trigger: rename one entity and run `pnpm layout` again with no change to the graph. The entities can move. The relaxation comment says "one corpus gives one picture", and layout.test.ts checks this only for an input with the same order. Add `ORDER BY id` to the two reads, and `ORDER BY src_id, dst_id` to the links read.
   - verify agent's proof: packages/worker/src/layout-job.ts line 9 is `const ENTITIES = 'SELECT id FROM public.entities'`. Lines 10-11 are `SELECT src_id, dst_id FROM public.relations WHERE src_kind = 'entity' AND dst_kind = 'entity'`. Neither query has an ORDER BY. runLayout (lines 25-33) gives these rows to entityLayout in the order that the database returns them. It does not sort them first.

In packages/worker/src/layout.ts the result depends on that order:
(1) topologyOf (line 57-58) gives each node its index from the input position.
(2) componentsOf (line 97) sorts the components with `two.length - one.length || numberAt(one, 0) - numberAt(two, 0)`. When two components have the same size, the one with the lower input index wins the centre and the earlier packing slots.
(3) relaxationOf (lines 250-253) sets each seed from the index of its member: `reach: extent * Math.sqrt(index / count), angle: index * GOLDEN_ANGLE`. A different order gives different start points.
(4) The order of the neighbour Sets (line 65-69) and of edgesOf (line 106-115) comes from the order of the links. This changes the BFS member order and the order of the floating-point sums.

The file's own test, layout.test.ts line 59-64, shows the order dependence: `entityLayout(['b', 'a'], [])` puts `b` at the origin only because `b` comes first in the list. The determinism test at line 42-46 calls the function two times with the same array, so it does not catch this.

SQL gives no order guarantee when a query has no ORDER BY. In PostgreSQL, an UPDATE of an entities row (for example, a rename) writes a new tuple version at a different place in the heap. After that, a sequential scan can return the rows in a different order even though the graph is the same. Thus two runs of `pnpm layout` on the same corpus can give a different picture. This goes against the comment at lines 245-246, "one corpus gives one picture".

The proposed fix is safe. `ORDER BY id` on the entities read and `ORDER BY src_id, dst_id` on the links read change only the input order, which the code already treats as arbitrary. Severity minor is correct.

### Issues

1. **runOnce claims any queued job, and every queued job is a document-ingestion job from put_document. It then runs a corpus-wide layout or reconcile against that job, ignores its document, never ends it on success, and on a third-attempt fault writes `failed` onto a document's ingestion job.**
   - file: `packages/worker/src/run-once.ts`:50
   - severity: major
   - review agent's proof: The only thing that enqueues is put_document (db/apply/40_functions.sql:185, `INSERT INTO public.jobs (document_id)`), and api.job describes a row as "One unit of work behind the ingestion door, and one row per document that entered it". runOnce does `const job = await claimJob(on);` and then `runAs(kind, ...)`, where `kind` comes from `process.argv[2]` (main.ts:10). `job.documentId` is never read. Trigger: the operator ingests document D, so a queued job for D exists, and then runs `pnpm worker:layout`. The layout worker claims D's job, sets it `running` and spends one of its 3 attempts (T9a), then runs a layout that has nothing to do with D. On success no door ends the row, so it stays `running` until release_expired_claims puts it back in the queue. D then never reaches extraction. The worker has no admission check that ties the claimed row to the work it does. It writes state onto rows it has no reason to own, and a future extraction worker loses those jobs. Fix: layout and reconcile are corpus-wide and never queued, as layout-main.ts and reconcile-main.ts already say, so keep them off the queue. Or add a kind to the job row and make claim_job take only rows of the caller's kind.

2. **The worker ends a job by id alone. If this worker's lease expired and another worker re-claimed the row, this worker's late failure marks the other worker's live claim `failed`.**
   - file: `packages/worker/src/run-once.ts`:61
   - severity: minor
   - review agent's proof: `await on.query(FAIL, [job.id, reason]);` passes only the id, and fail_job (db/apply/40_functions.sql:525-527) matches `WHERE id = p_id AND status = 'running'`. It does not check `claimed_by = session_user`, `claimed_at` or `attempts`. Trigger: worker A claims a job at attempt 3 and runs longer than job_claim_lease_seconds (900 s, 95_seed.sql:92). The operator calls release_expired_claims, and worker B claims the row (attempt 4, running). Then A's run throws, and A calls fail_job. The row is `running`, so the update succeeds and ends B's live claim with A's reason. Any gabriel_agent session can also end any running job it never claimed. Fix: the worker passes the attempt count it claimed with (`job.attempt`), and fail_job matches `attempts = p_attempt AND claimed_by = session_user`.
   - verify agent's proof: I read the files myself. The finding is a real defect.

1. packages/worker/src/run-once.ts:61 calls `await on.query(FAIL, [job.id, reason]);` with `FAIL = 'SELECT public.fail_job($1, $2)'` (line 21). The call sends only the id and the reason. It does not send the attempt count that the worker holds in `job.attempt` (line 58).

2. db/apply/40_functions.sql:525-527, the body of fail_job:
   `UPDATE public.jobs SET status = 'failed', failure_reason = p_reason, finished_at = now(), updated_at = now() WHERE id = p_id AND status = 'running';`
   The only guard is `status = 'running'`. It does not check `attempts`, `claimed_at` or `claimed_by`.

3. Claims can pass from one worker to another:
   - release_expired_claims (40_functions.sql:499-504) sets a `running` row whose `claimed_at + lease < now()` back to `queued`, and it keeps the attempt count.
   - claim_job (lines 467-474) takes the row again and sets `status = 'running'` and `attempts + 1`.
   - The lease is 900 s (db/apply/95_seed.sql:92).

   The failure sequence:
   - Worker A holds attempt 3 and runs for more than 900 s.
   - release_expired_claims puts the row back in the queue.
   - Worker B claims the row at attempt 4, so the row is `running` again.
   - A's run throws. Because `job.attempt` (3) >= JOB_RETRY_LIMIT, A calls fail_job(id, reason).
   - The row is `running`, so the UPDATE matches. B's live claim becomes `failed`, with A's reason and a `finished_at` value, while B still runs.

   The run-once.ts comment at lines 17-18 says that the lease returns stalled rows to the queue. So in this design, the lease hands the row to a new worker before the old worker has stopped.

4. db/apply/90_grants.sql:66 grants fail_job to gabriel_agent. Any agent session can therefore fail any running job by id.

Note on the fix. All workers connect as gabriel_agent. So `claimed_by = session_user` does not tell two workers apart: claimed_by is the connection role (20_views.sql:171). The check that closes the race is the attempt match (`attempts = p_attempt`). The finding is minor. The row was already at its last attempt, and B would also end it as `failed` if B's run failed. The harm is a false `failed` status with the reason of a different run, while B's run is still live or has succeeded.

The root package.json:38-39 holds `worker:layout` and `worker:reconcile`. Lines 40-41 hold `layout` and `reconcile`, which go to the hand-run entry points. A grep finds `runOnce`, `JOB_KIND`, `main.ts` and the worker:* scripts only in main.ts, run-once.test.ts and package.json. No other package imports @gab/worker. No CI job or doc refers to the worker:* scripts.

The removal is safe. The `claim_job` and `fail_job` doors do not change, and the perimeter tests (tools/perimeter/role-privilege.db-test.ts) test these doors directly in SQL. Two small follow-ups:
- packages/worker/package.json "exports": "./src/main.ts" must change or be removed.
- If claim.ts is deleted, claim.db-test.ts must go too. The proposal already gives the option to keep `claimJob`.
   - decision conflict claimed: T9a says the worker applies the 3-attempt limit through `fail_job`, and run-once.ts is the only code that does. Removing it does not change the rule. It removes the only runner, and that runner has no per-document work to retry. The rule and its call to `fail_job` come back with the first runner that processes a document. So T9a stays locked, and its Consequence line must say that no worker applies it yet.
   - verify agent's check: T9a (docs/decisions.md:348-352) sets a rule: 3 claims per job, and on the 3rd failure the job is marked failed through `fail_job`, which is granted to `gabriel_agent`. The rule is about the database door and the attempt limit. It does not require a layout or reconcile runner. The proposal removes the only TypeScript code that calls `fail_job`, but the door, its grant and its perimeter tests stay. It is not necessary to reopen T9a. At most, add one line to the Consequence of T9a that says no worker calls `fail_job` yet, until the per-document runner exists. That is a note, not a reversal of the decision. The proposal does not break any locked decision. It puts back the earlier rule in reconcile-main.ts:7-9 and commit 1e73ee4, which say that corpus-wide runs are never job rows.

2. **The backoff waits in the process after the claim, so it delays nothing except the process exit, and its 30-second cap cannot be reached.**
   - file: `packages/worker/src/backoff.ts`:8
   - severity: proposal
   - review agent's proof: Current shape: `runOnce` claims the row, which is then `running`, and next does `await wait(backoffMs(job.attempt))` (run-once.ts:53). The row is already taken, so the wait does not space two attempts. The next attempt comes only after the lease expires (`job_claim_lease_seconds` = 900, 95_seed.sql:92), and as the issue above shows, nothing runs that expiry. With `JOB_RETRY_LIMIT = 3` the largest wait is `backoffMs(3)` = 4000 ms. The `MAX_DELAY_MS = 30_000` cap applies only from attempt 6, which the limit is meant to prevent. Proposed shape: delete backoff.ts, backoff.test.ts, `wait` and its call in run-once.ts, and the fake timers in run-once.test.ts (lines 42-48, 92-103). Why it is safe: the lease alone controls the spacing between claims, and a wait of 1 to 4 seconds before a 900-second lease has no effect. The column comment in 0004_jobs.sql:20-23 already says that a growing wait cannot be computed from this table.
   - verify agent's proof: packages/worker/src/backoff.ts:8-9 computes `Math.min(MAX_DELAY_MS, BASE_DELAY_MS * 2 ** Math.max(0, attempt - 1))`, with MAX_DELAY_MS = 30_000 (line 5). There is one caller only, packages/worker/src/run-once.ts:53, `await wait(backoffMs(job.attempt));`. This call comes after `claimJob(on)` at line 50. claim_job (db/apply/40_functions.sql:449-478) sets the row to `status = 'running'`, increments `attempts` and stamps `claimed_at` in its own statement. The row is taken before the wait starts, so the wait does not delay or space a claim. It only delays the run and the exit of the one-shot process in main.ts, which runs `runOnce` one time and then calls `client.end()`. A new attempt comes only after release_expired_claims (40_functions.sql:488-508) puts a `running` row back to `queued` when `claimed_at + lease < now()`, and the lease is 900 s (95_seed.sql:92). A wait of 1-4 s after a gap of at least 900 s has no effect. JOB_RETRY_LIMIT = 3 (run-once.ts:19): on attempt >= 3 a failure calls fail_job, so the normal largest wait is backoffMs(3) = 4000 ms. The 30 s cap applies only from attempt 6 (2^5 * 1000 = 32000). Attempt 6 can occur only if the worker stops without the catch path (a crash) on attempts 3, 4 and 5, because claim_job enforces no limit. Thus "cannot be reached" is correct for all normal paths and nearly correct for the others. To delete the wait is safe: only run-once.ts imports backoffMs, and only backoff.test.ts and the fake-timer test "a lost claim waits longer" (run-once.test.ts:92-103) plus the useFakeTimers hooks (42-48) and the runAllTimersAsync calls depend on it. These tests must be removed or simplified together with the wait. The 0004_jobs.sql:20-23 comment also says that the growing wait of #25 cannot be computed from this table.

## False alarms (rejected candidates, logged for audit only)

1. [Correctness and edge cases] The two reads and the layout write are not in one transaction, so a merge that is promoted during the run makes the full layout write fail on the foreign key. (packages/worker/src/layout-job.ts) — rejected: The three statements do run as separate autocommit queries. See packages/worker/src/layout-job.ts:25 (`on.query(ENTITIES)`), :27 (`on.query(LINKS)`) and :35 (`on.query(WRITE, ...)`). A delete that commits between line 25 and line 35 does make the INSERT in set_entity_layout fail on entity_layout_entity_fkey (db/migrations/0005_entity_layout.sql:23). But the finding is wrong on three points:

(1) The named trigger does not exist. A merge cannot land. The merge branch of the promotion function is `RAISE EXCEPTION 'the operation % has no write path yet. M12 needs an alias table ...'` (db/apply/40_functions.sql:398-402). Line 382 is in the delete_entity branch, not in a merge branch. Only a delete_entity promotion can cause this race.

(2) The stop is the documented behaviour. The header of set_entity_layout (db/apply/40_functions.sql:540-541) says: "AN UNKNOWN IDENTIFIER STOPS THE WHOLE RUN, by the foreign key. A run reads the entities and places them, so an identifier that no entity carries says the run and the record disagree." The function empties and fills the table in one transaction (lines 548-552). A failed run therefore changes nothing: the previous positions stay, and no data becomes incorrect. In job mode, run-once.ts gives the run up to 3 claims (JOB_RETRY_LIMIT), and the lease puts the job back in the queue. In by-hand mode (layout-main.ts), the operator runs the job again. The "skip ids that no longer exist" fix goes against this recorded choice.

(3) The main fix does not remove the failure. With REPEATABLE READ, the FK check against a row that was deleted after the snapshot still fails, because PostgreSQL raises a serialization error. The finding says this itself: "the write can still fail at commit". The only result would be that the two reads agree with each other, and the finding does not show a defect from reads that do not agree.

The result is a transient, retried and atomic failure that the design expects. This is not a correctness defect.
2. [Security] Every worker entry point is started with the whole infra/.env file. The worker process therefore holds the owner, gabriel_app and MinIO root secrets, which breaks the "one process holds one secret" boundary that the grants depend on. (package.json) — rejected: The launch facts are correct. In package.json, lines 38-41 start all four worker entry points with `node --env-file=infra/.env ...`, for example line 38: `"worker:layout": "node --env-file=infra/.env packages/worker/src/main.ts layout"`. infra/.env holds POSTGRES_PASSWORD, MINIO_ROOT_USER/PASSWORD, GABRIEL_APP_PASSWORD, GABRIEL_AGENT_PASSWORD, GABRIEL_READ_PASSWORD and RAW_STORE_ACCESS_KEY/SECRET_KEY. I read the key names only, not the values. packages/worker/src/address.ts:13 parses GABRIEL_AGENT_PASSWORD only. db/apply/90_grants.sql says "ONE PROCESS HOLDS ONE SECRET". So the worker process does hold wider secrets than it uses.

But this is not an unknown defect. It is a limit that a locked decision records and accepts. docs/adr/0002-local-runtime.md section 7 ("Secrets") says: "Two limits, written down because they are easy to believe away. Every entry point loads the environment file whole, so the root pair sits in the same process as the application pair: the account bounds the client, and it does not bound the process." The design therefore states on purpose that every entry point, the worker included, gets the whole env file, and that an account bounds a client but does not bound the process. The finding says "claimed decision conflict: none", and that is wrong. To report it, we must reopen ADR 0002 section 7, and the finding does not argue for that.

Also, the escalation path that the finding names is not in the code now. The worker runs only layout and reconcile (packages/worker/src/main.ts, layout-main.ts, reconcile-main.ts). No model runs over untrusted text yet. The runtime is local and on the loopback address only (ADR 0002 section 4). What is left is a general "compromised dependency" risk. That risk applies to every entry point in the same way, and the ADR accepts it for the whole runtime. It is a hardening idea for later, not a confirmed major defect. I am not sure it is safe to report as a new finding, so the verdict is FALSE_ALARM.
3. [Security] The reconcile run, which only lists the bucket, opens the raw store with the PutObject-capable application account, so a read-only worker path can overwrite raw evidence. (packages/worker/src/run-once.ts) — rejected: The facts in the description are correct, but the security effect is not real. Line 35 of packages/worker/src/run-once.ts is `const found = await reconcileCorpus(on, openRawStore());`. packages/worker/src/reconcile.ts calls only `listKeys` (ListObjectsV2Command in packages/store/src/listing.ts). `openStore` in packages/store/src/bucket.ts:44-58 signs with RAW_STORE_ACCESS_KEY/RAW_STORE_SECRET_KEY. infra/docker-compose.yml:87-90 attaches infra/minio/policy-raw-write.json to that account, and the policy grants `s3:PutObject` on `raw/*`.

The finding still fails, for these reasons:

(1) The worker process already holds the MinIO root pair. package.json:38-41 starts every worker entry (`worker:layout`, `worker:reconcile`, `reconcile`) with `node --env-file=infra/.env`. infra/.env.example shows that this file holds MINIO_ROOT_USER and MINIO_ROOT_PASSWORD next to the RAW_STORE keys. The comment in bucket.ts:25-27 states this directly: "It may write over a key that exists, and the root pair sits in the same process, so neither of those is stopped here." A list-only account for the reconcile path would therefore not narrow what the process can do. The root credential in the same environment can overwrite and delete anything. The proposed fix does not remove the exposure it names.

(2) No code on the reconcile path sends a write. The call chain is reconcileCorpus -> listKeys -> ListObjectsV2Command, and no input can turn that call into a PutObject. The worker is a local CLI with no network listener.

(3) T3 in docs/decisions.md:302-309 accepts this overwrite exposure on purpose ("Evidence rests on the care of one operator"). T3 names versioning, object lock or a content-hash key as the repair, not credential splitting.

What remains is a least-privilege preference that gives no measurable gain. It is not a confirmed defect.
