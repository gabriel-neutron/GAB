3. [Architecture and ADR conformance] Two branches that return the same object can be one branch. (src/features/detail/rename-draft.ts) — rejected: The duplicate branches are real. src/features/detail/rename-draft.ts:28-31 reads `if (label !== null) return { ready: true, act: { op: 'update_entity', targetId: entityId, label, type } }; if (type !== null) return { ...same literal... };`. But the duplication is there on purpose. It is needed for type narrowing, so the proposed merge is not safe. The act type is `Extract<ElementAct, { op: 'update_entity' }>`. In src/shared/write/elements.ts:15-18 that type is a union: `{ label: string; type: string | null } | { label: null; type: string }`. This union makes "change nothing" (label null and type null) impossible to express. Each branch in rename-draft.ts narrows one variable. Line 28 makes `label` a `string`, so the object matches the first member. Line 30 runs only when `label` is null and makes `type` a `string`, so the object matches the second member. If you merge the two into `if (label !== null || type !== null)`, TypeScript does not narrow either variable, because it does not track a correlation between two separate variables. The literal would then be `{ label: string | null; type: string | null }`, and TypeScript cannot assign that to the union: the (null, null) case matches neither member. The merge therefore breaks the type check (a tsc error). The alternative is a cast, which removes the compile-time guarantee that the writer never gets a no-op act. The tests would still pass at runtime, but the proposal says the change "is safe". That claim is wrong, because typecheck fails.

6. [Simplification and structural discipline] `save.ts` and `structure.ts` are two parallel copies of one act state machine. The page also copies the send-and-settle handler three times and uses two live regions for one queue. (src/features/detail/structure.ts) — rejected: The duplication in the code is real. The proposed shape is not safe as the finding states it, because one part of it causes a regression. A report that says the whole shape is "safe" would be wrong.

What I confirmed:
- save.ts:55-62 `saveClaims` and structure.ts:101-114 `changeStructure` both take a `WriteOutcome` from `sendAct` in shared/write/door.ts. Both map `outcome.state` signed/undecided/unknown/refused to a step with the same branches. The only difference is that structure.ts adds `deed: act.op`.
- `SaveState` (save.ts:11-17) and `StructureState` (structure.ts:9-20) have the same six steps. Only the busy step has a different name: 'saving' against 'working'.
- detail-page.tsx `onSave` (89-100), `onMint` (104-112) and `onStructure` (116-124) have the same pattern: guard `busy`, set the busy step, await, set the state, stop if not 'signed', then call a follow-up. Line 67 ORs the two machines: `const busy = structure.step === 'working' || save.step === 'saving';`.

So one `settle(outcome, deed)` and one `run` handler with an after-signed callback would be safe.

What breaks: the "one SaidLine" part. The two live regions do not carry the same sentences.
1. `saveSaid` has an idle case with no deed: save.ts:49-50 `case 'idle': return calm(edit.ready ? ready(edit.count) : edit.reason);`. This line stands beside the Save button (save-bar.tsx) and tells the analyst whether the pending edit can be saved. `structureSaid` idle is `calm('')` (structure.ts:81-82). With one line, a structure sentence ("The relation is deleted...") would hide the readiness or refusal sentence of the pending edit. Or the readiness sentence would hide the structure outcome. The claim "the words tables stay keyed by deed" does not cover this, because the idle step has no deed.
2. detail-page.tsx:81-84 `onEdit` resets only the save machine on a keystroke: `setSave((current) => (current.step === 'saving' ? current : IDLE));`. With one state, a keystroke would clear a structure 'unknown' interrupt. structure.ts:49-50 says that interrupt must stay, because "a delete that reads as refused destroys evidence in silence".

To keep these behaviours, the merged design would need special cases that bring back the two-line split. The narrower opportunity (one shared settle mapping and one handler, with two state slots and two live regions kept) is real. But the finding as written recommends a shape that would break the idle readiness line and the keystroke-clear scope.
7. [Simplification and structural discipline] Every draft value is parsed twice: `typedInto` runs `readEntry` and keeps only the refusal, and `pendingEdit` runs `readEntry` again on the same text to get the value. (src/features/detail/draft.ts) — rejected: The duplicate parse is in the file. `typedInto` (draft.ts:75) calls `readEntry(claim.value.control, typed)` and keeps only the refusal. `pendingEdit` (draft.ts:116) calls `readEntry(claim.value.control, entered(draft))` again. `entered` (130-131) gives back the same text as `typed` when the first read held.

The proposal is still not safe. It says both calls take the same control, and that the second `!read.held` branch (117-120) cannot occur. Both claims are wrong. The two calls read `claim.value.control` from two different `rows` arrays:
- `typedInto` uses the rows at the time of the keystroke (`detail-page.tsx:83`, `typedInto(dossier.rows, ...)`).
- `pendingEdit` uses the rows of the current render (`detail-page.tsx:77`, `pendingEdit(dossier.rows, drafts)`).

`dossier.rows` changes while a draft stays:
- A draft is kept across reloads. After a save, `onSaved()` reads the record again. `draftsAfterSave` (draft.ts:87-93) keeps on purpose every key that was typed again while the act was in flight.
- Structure acts and reads from other writers also refresh the dossier.
- The control comes from the shape of the stored value (`claims.ts` `shapeOf`), so a reload can change it. Example: text `2019-02-03` saved in a 'text' cell comes back as a string that `isDay` accepts, so the control becomes 'date'. Another example: an agent writes a number over a text value.

Concrete case: the analyst types `2019-02-03` into a text cell and saves. While the act is in flight, the analyst types `2019-02-03 approx`. At the keystroke the control is 'text', so the refusal is null. After the reload, the control is 'date'. Today `pendingEdit` reads the draft again as 'date' at line 116, gets a refusal, and blocks the save at lines 117-120. So that branch can occur.

If the proposal stores the `ClaimEntry` once at the keystroke, `pendingEdit` would send a value read under the old control, and it would not refuse. That changes what the save carries, so the change is not a behaviour-preserving simplification.

A second, smaller problem: `ClaimDraft` is also the prop type of `Field`. `field.tsx:133` and `field.tsx:188` read `draft.refusal`, and `record.tsx:58` and `field.stories.tsx:60/73/94` build drafts with a `refusal` field. The change described therefore touches more than draft.ts.
