1. **The promotion step of a signed act reads a lost answer with refusalFrom and not with failureFrom, so a promotion that committed can be reported as 'refused, and the act stays pending'.**
   - file: `packages/writer/src/sign.ts`:241
   - severity: major
   - review agent's proof: The catch at lines 236-242 returns `{ outcome: 'undecided', reply: { refusal: refusalFrom(cause, proposalId), proposalId } }` for every failure. decide.ts uses failureFrom to part a refusal from a doubt, and refusal.ts line 101 says 'no caller may report one as a refusal'. sign.ts does not obey this rule. Trigger: the COMMIT of the promotion transaction goes to the server, and then the socket dies (ECONNRESET, or a server stop with 57P01). The promotion can stand in the record. refusalFrom then gives one of two sentences. For ECONNRESET or a codeless error, BY_CODE and BY_SHAPE do not match, so the reply is `named(GENERIC, proposalId)` = 'the database refused the act, and the act stays pending as <id>'. For 57P01 or ETIMEDOUT, the reply is UNREACHABLE = 'the database did not answer, and nothing was written'. Both sentences can be false. The operator then decides the act a second time, or signs it again. Fix: at line 241, call failureFrom(cause). Use the doubt sentence when `raised` is false, and keep refusalFrom(cause, proposalId) only when `raised` is true.
   - verify agent's proof: I read packages/writer/src/sign.ts. Lines 233-243 run the promotion in a second transaction (`inTransaction(client, () => promote(client, proposalId))`). The catch sends every failure to `refusalFrom(cause, proposalId)` at line 241, and it gives the outcome 'undecided'. This path never calls `failureFrom`. sign.ts imports only `refusalFrom` (line 7).

In packages/writer/src/refusal.ts, `failureFrom` (lines 102-106) holds the only test that tells a refusal from a doubt. `raisedBy` (line 97-98) accepts a code only if it is a 5-character SQLSTATE that is not class 08 and is not in DOUBTFUL (ECONNRESET, EPIPE, ETIMEDOUT, 57P01, 57P02, 57P03, ...). The doc comment at line 101 says: "Every other failure is a doubt, and no caller may report one as a refusal." decide.ts lines 60-64 obeys this rule for the same PROMOTE_PROPOSAL statement, and it returns the DOUBT sentence ("the record gave no answer to read, and the act may have run whole") when `raised` is false.

sign.ts does not obey the rule. Assume that COMMIT (line 55) goes to the server and then the connection is lost. The COMMIT can land. Then inTransaction's catch also runs ROLLBACK on the dead client, and the error from that call replaces the first error. That error is typically a codeless Error such as "Connection terminated", or ECONNRESET. `refusalFrom` finds no BY_CODE or BY_SHAPE match for it. It returns `named(GENERIC, proposalId)`, which is "the database refused the act, and the act stays pending as <id>" (lines 61-62, 70). For 57P01 or ETIMEDOUT, it returns UNREACHABLE, "the database did not answer, and nothing was written" (lines 5, 19, 24).

The UI shows this text. src/features/detail/save.ts line 32-33 and line 46 show "The change was written as the proposal X, and it was not signed. <refusal>". The screen thus says that the act was not signed and stays pending, but the promotion can be in the record. The operator can then decide the act again or sign it again. The defect is real. The proposed fix is safe because it copies the pattern in decide.ts: call failureFrom(cause), use the doubt sentence when `raised` is false, and keep refusalFrom(cause, proposalId) when `raised` is true.

3. **inTransaction awaits ROLLBACK in its catch, so a failed ROLLBACK replaces the original error and the caller classifies the wrong error.**
   - file: `packages/writer/src/sign.ts`:58
   - severity: minor
   - review agent's proof: `} catch (cause) { await client.query('ROLLBACK'); throw cause; }`. Trigger: the connection breaks during propose_change or promote_proposal, for example with 57P01 or ECONNRESET. pg marks the client as not queryable. `client.query('ROLLBACK')` then rejects at once with 'Client has encountered a connection error and is not queryable', and that error has no `code`. In the promote path, it returns 'the database refused the act, and the act stays pending as <id>'. Fix: `await client.query('ROLLBACK').catch(() => undefined); throw cause;`.    - verify agent's proof: packages/writer/src/sign.ts lines 51-61 read: `} catch (cause) { await client.query('ROLLBACK'); throw cause; }` (the ROLLBACK is at line 58). There is no catch on the ROLLBACK. If the ROLLBACK rejects, its error replaces `cause`.

The installed driver is pg@8.23.0 (packages/writer/node_modules/pg). In lib/client.js, `_handleErrorEvent` (about line 420) sets `this._queryable = false` when the socket dies, for example with ECONNRESET. `query()` (lines 747-750) then rejects each new query with `new Error('Client has encountered a connection error and is not queryable')`. That error has no `code`. For a server shutdown (57P01), the active query gets 57P01. So in both cases the ROLLBACK at line 58 rejects with a codeless error, and the real cause is lost.

The callers at lines 228-231 and 234-242 give that error to `refusalFrom` (packages/writer/src/refusal.ts:65-71). `wordOf(cause,'code')` returns ''. BY_CODE has no match, and no BY_SHAPE entry matches either message. The function therefore returns GENERIC 'the database refused the act'. The proposed fix is safe. pg-pool@3.14.0 index.js line 392 removes a client on release when `!client._queryable || client._ending`, so a broken client never goes back to the pool if the ROLLBACK error is ignored. A normal SQL refusal (for example 23505) does not break the connection, so the ROLLBACK succeeds and that path does not change. Severity is minor: only the text of the message is wrong, and the outcome kind stays the same.

## Security

### Issues

1. **The writer never checks the Host header, so a hostile web page can use DNS rebinding to write into the evidentiary layer through the operator's browser.**
   - file: `packages/writer/src/admission.ts`:22
   - severity: major
   - review agent's proof: `turnedAway` tests only `sec-fetch-site` and `content-type`. main.ts:8-14 binds 127.0.0.1:5177, and the port is fixed and public in the repository. Trigger: the operator opens a page on `attacker.example`, which can be the site of an entity under investigation. The page's DNS record then changes to 127.0.0.1, and the page calls `fetch('http://attacker.example:5177/write/delete-entity', {method:'POST', headers:{'content-type':'application/json'}, body:'{"targetId":"..."}'})`. To the browser this request is same-origin, so it sends `Sec-Fetch-Site: same-origin`, sends no preflight, and passes both tests. The writer then signs creates, updates, deletes and promotions as the operator, and the CC-BY dataset publishes them. The page can also read each reply, because it is same-origin. The Vite dev server has its own host check, but the page goes directly to port 5177 and not through Vite. Fix: refuse any request whose `Host` is not `127.0.0.1:5177` or the dev-server host that the proxy forwards (`localhost:5173`, because `changeOrigin` is not set).
   - verify agent's proof: packages/writer/src/admission.ts lines 22-28: `turnedAway` reads only two headers. Line 23-24 refuse a request only when `sec-fetch-site` is present and not 'same-origin'. Lines 25-26 refuse a body type other than application/json. The file does not read `Host` or `Origin`. packages/writer/src/routes.ts line 24 applies only `admitOwnSiteJson()` to '/write/*', and the POST doors (lines 26-38) go directly to `sign`/`decide`. A search of packages/writer/src for host/origin/cors finds no other check. packages/writer/src/main.ts lines 8-9 and 14 bind 127.0.0.1:5177, so a request that arrives at the loopback socket with any Host value is accepted. vite.config.ts line 23 proxies '/write' to http://127.0.0.1:5177, but a page that the browser loads from a rebound name goes directly to port 5177. In a DNS rebinding attack, the browser sees the origin as attacker.example:5177 for the page and for the fetch, so it sends `Sec-Fetch-Site: same-origin` (this passes line 24). A same-origin fetch with content-type application/json sends no CORS preflight, so it passes lines 25-26 too. The writer then signs the write. The comment in vite.config.ts lines 20-22 says that the writer "holds its own rule on the sender", but that rule does not bind the request to the expected host. Limit on the effect: Chrome's Local Network Access protections can stop some public-to-loopback requests. Firefox and Safari do not give that protection, and the server must not depend on it. The defect is real, and a Host allow-list (127.0.0.1:5177, and localhost:5173 as the proxy forwards it because changeOrigin is not set) is the correct fix.
