3. **fail_job does not check that the caller holds the current claim, so a stale worker can fail a job that a second worker runs now.**
   - file: `db/apply/40_functions.sql`:527
   - severity: minor
   - review agent's proof: fail_job does `UPDATE public.jobs SET status = 'failed' ... WHERE id = p_id AND status = 'running'`. It does not compare claimed_at or the attempt number with the claim the caller took. Concrete sequence: worker A claims the job on attempt 3 and runs for more than job_claim_lease_seconds (900). The operator calls release_expired_claims, and the row goes back to 'queued'. Worker B claims it (attempt 4, status 'running'). Worker A then fails and calls fail_job(id, reason) because its attempt was >= 3 (run-once.ts:58). The row becomes 'failed' while B still runs it. B's later fail_job or success then finds a row that is not 'running'.    - verify agent's proof: db/apply/40_functions.sql:517 has the signature `fail_job(p_id uuid, p_reason text)`. It gets only the job id and a reason. It does not get the attempt number or the claim time. Its only guard is at lines 525-527: `UPDATE public.jobs SET status = 'failed', ... WHERE id = p_id AND status = 'running';`. Any caller that knows the id can therefore end whichever claim holds the row now.

Other functions in the same file let a second worker take the row. release_expired_claims (lines 499-504) sets `status = 'queued', claimed_at = NULL` on every running row where `claimed_at + v_lease < now()`. Nothing tells the first worker. The only writer of claimed_at is claim_job (grep finds no heartbeat or lease renewal). claim_job (lines 467-474) then sets `status = 'running', attempts = j.attempts + 1`. Its comment at line 442 says it enforces no limit, so a new worker can claim the row again.

A throws and calls fail_job(id, reason). The row is 'running', so the UPDATE matches and marks B's live run 'failed' with A's reason. B's later fail_job raises 'job % is not running'.

The defect is real. Minor severity is correct, because it needs a lease expiry during a last attempt. The fix is to guard on the claim: pass the claimed attempt and add `AND attempts = p_attempt`.
