1. **A job that runs without error is never ended: no door writes `done`, so the row stays `running` for ever and looks the same as a crashed or failed job.**
   - file: `packages/worker/src/run-once.ts`:56
   - severity: major
   - review agent's proof: `runOnce` returns `await runAs(kind, on, openRawStore)` and writes nothing to the job row on success. `db/apply/40_functions.sql` has `claim_job`, `release_expired_claims` and `fail_job`, and no door sets `status = 'done'` or `finished_at` (the comment in `db/migrations/0004_jobs.sql` says 'NO PATH WRITES done'). Trigger: `pnpm worker:layout` claims job J (attempt 1), the layout run succeeds, and J stays `running` with `claimed_at` set. The operator cannot tell J from a job whose worker crashed. If the operator runs `release_expired_claims()` to requeue the stuck jobs that T9a relies on, J goes back to `queued` too. J then runs again with attempt 2, then 3, and so on. If one of these later runs fails at attempt >= 3, `fail_job` marks a job that already succeeded as `failed`. The queue never drains.
   - verify agent's proof: In packages/worker/src/run-once.ts, lines 55-56 read `try { return await runAs(kind, on, openRawStore); }`. The success path returns the report line and sends no query to the job row. The only write to the row in this file is `SELECT public.fail_job($1, $2)` (line 21, used at line 61), and it runs only in the catch block when `job.attempt >= JOB_RETRY_LIMIT`. In db/apply/40_functions.sql, claim_job (lines 467-471) sets status = 'running', attempts + 1 and claimed_at. release_expired_claims (lines 499-504) sets every row `WHERE j.status = 'running' AND j.claimed_at + v_lease < now()` back to 'queued' and does not check whether the work succeeded. fail_job (lines 525-527) is the only function that writes finished_at, and it writes 'failed'. A grep of the whole repo (node_modules excluded) finds no function that writes status 'done': the value is only in the CHECK list and in the comment `NO PATH WRITES 'done'` in db/migrations/0004_jobs.sql:44. As a result, a job that runs without error stays 'running' with its claimed_at set. When its lease expires, the next call to release_expired_claims() (granted to gabriel_app in db/apply/90_grants.sql:65) puts it back in 'queued'. The worker then claims it again, and attempts goes up. If a later run of the same job fails at attempt >= 3, fail_job marks the job 'failed' although an earlier run succeeded. The job never reaches an end state on success, and the operator cannot tell it from a crashed claim.

5. **A lost COMMIT of the proposal transaction is reported as a 422 refusal, but the pending proposal may exist. A retry then writes a second proposal.**
   - file: `packages/writer/src/sign.ts`:230
   - severity: minor
   - review agent's proof: `catch (cause) { return refused(refusalFrom(cause)); }` treats every failure of `inTransaction(client, () => propose(client, act))` as a refusal. Trigger: the socket drops after COMMIT is sent. `inTransaction` then runs ROLLBACK on the dead client, and that throws a second error with no code, which replaces the first one. `refusalFrom` maps it to GENERIC 'the database refused the act', with status 422 and no `proposalId`. The proposal may be committed and `pending` in the queue. The operator reads 'refused' and signs the act again, so two pending proposals exist, and the first one has no reply that names it. Fix: use `failureFrom` here as `decide.ts` does, and send a doubt, not a refusal, when no SQL state was raised.
   - verify agent's proof: I read packages/writer/src/sign.ts myself. Lines 227-231 are `try { proposalId = await inTransaction(client, () => propose(client, act)); } catch (cause) { return refused(refusalFrom(cause)); }`. `refused` (line 32) gives outcome 'refused', and packages/writer/src/routes.ts:12 maps it to `refused: 422`. It also gives no proposalId. `inTransaction` (lines 51-61) sends COMMIT at line 55. If the COMMIT fails, the catch at line 58 does `await client.query('ROLLBACK')` without a guard. On a dead connection, that second query throws, and its error replaces the first cause.

In packages/writer/src/refusal.ts, `refusalFrom` (lines 65-71) reads only `code` and `message`. A pg client-side error such as "Connection terminated unexpectedly" or "Client was closed and is not queryable" has no code in BY_CODE and no BY_SHAPE match, so the function returns GENERIC 'the database refused the act'. Some codes do match. ETIMEDOUT and ECONNREFUSED map to UNREACHABLE, 'the database did not answer, and nothing was written', and in this case that sentence is false. The window is small because the socket must drop after COMMIT is sent. But the code is inconsistent with the doubt/refusal split that refusal.ts itself documents ("no caller may report one as a refusal"), so the defect is real. Minor severity is correct.

## Security

### Issues

1. **The writer admission reads only Sec-Fetch-Site and Content-Type, and it never checks the Host or the Origin. A DNS-rebinding page can therefore sign acts straight into the evidentiary layer.**
   - file: `packages/writer/src/admission.ts`:22
   - severity: major
   - review agent's proof: The writer binds 127.0.0.1:5177 (packages/writer/src/main.ts:8-9). The only guard on every door is `turnedAway` in admission.ts:22-28: `if (site !== null && site !== OWN_SITE) return { status: FORBIDDEN ... }` and a check for an `application/json` media type. No code reads `Host` or `Origin`, and Hono does not check them either. The attack: the operator visits a hostile page at http://evil.example:5177. The attacker's DNS then rebinds evil.example to 127.0.0.1, and the page calls `fetch('/write/create-entity', {method:'POST', headers:{'content-type':'application/json'}, body: ...})`. To the browser this request is same-origin, so it sends `Sec-Fetch-Site: same-origin`, sends no preflight, and lets the page read the reply. The guard admits the request. `sign` (sign.ts:198-247) then proposes and promotes in two transactions as `gabriel_app`, and writer.db-test.ts shows that `src: ['manual']` is accepted on this path. The result is a forged entity, attribute or relation in the evidentiary layer, cited on the operator's own authority, and a `delete_entity` or `promote_proposal` works the same way. Firefox has no general block against DNS rebinding. The project records the people under investigation as adversaries who watch the published dataset (PU1), and journalists cite that dataset. The fix is small: refuse a request whose `Host` is not in an allowlist (`127.0.0.1:5177`, plus the Vite origin `localhost:5173` / `127.0.0.1:5173`, because the proxy keeps the original Host). Also refuse a request whose `Origin` header is present and not in that same list. Add the matching cells to admission.db-test.ts. Note also that line 20 allows an absent site header, so any local process (for example an AI agent on the operator's machine) reaches every door, the promotion included. C5 accepts that, and it is not part of this finding.
   - verify agent's proof: I read the files myself. In packages/writer/src/admission.ts:22-28, the only admission test reads two headers. At line 23 it reads `headers.get('sec-fetch-site')`. At line 24 it refuses only when the value is present and is not 'same-origin'. At lines 25-26 it refuses a media type other than application/json. No line in admission.ts reads `host` or `origin`. A grep for host, origin and rebind in packages/writer/src finds only the constant 'same-origin' and the bind hostname in main.ts. routes.ts:24 attaches this middleware as the only guard (`app.use('/write/*', admitOwnSiteJson())`). Lines 26-38 then send the raw body directly to `sign` or `decide`, with no token and no other check. main.ts:8-14 binds the server directly on 127.0.0.1:5177, so a browser can reach it without the Vite proxy (the Vite dev server has its own allowedHosts check, but that check does not protect port 5177). In a DNS-rebinding attack, a page loaded from http://evil.example:5177 that then resolves to 127.0.0.1 sends a same-origin fetch. The browser marks it `Sec-Fetch-Site: same-origin` and sends `Content-Type: application/json` with no preflight, and the Host header is `evil.example:5177`. admitOwnSiteJson admits this request, and the create, delete and promote doors run. Chromium's Private/Local Network Access can partly block this. Firefox has no general block. The defect is real: the writer never checks that the Host is its own. A Host allowlist (with an Origin check when the header is present) closes the hole, and this fix does not conflict with the absent-header allowance at lines 19-21.

7. [Simplification and structural discipline] The `exports` fields of @gab/writer and @gab/worker point at scripts that start a server or run a job on import, and the root devDependency on @gab/writer is not read by anything. (packages/writer/package.json) — rejected: The facts in the description are correct, but the proposed change is not safe. packages/writer/package.json:6-8 has `"exports": { ".": "./src/main.ts" }`. main.ts calls `serve(...)` at the top level (packages/writer/src/main.ts:11-14). The root package.json:49 has `"@gab/writer": "workspace:*"`. No source file imports `@gab/writer` or `@gab/worker`. My grep outside node_modules finds these names only in the package.json files and in pnpm-lock.yaml.

The root devDependency is there for a reason: it keeps the lint guard active. Commit 1bea7b8 added it together with `@gab/model`. The commit message says: "The lint refusal of `@gab/model` did not fire... the name did not resolve, and the rule reports nothing for a name it cannot resolve. `@gab/writer` resolved only through an artefact of the install. The root now declares both packages, so both names resolve and both refusals fire."

The rule that relies on this is in eslint.config.ts:525-549. It is a boundaries `disallow` that applies to an element of `type: 'package'` with `captured: { pkg: [...NODE_PACKAGES] }`, where NODE_PACKAGES = ['writer', 'model', 'store', 'worker'] (line 26). This rule stops shared, feature, route and package files from importing the writer. Its message is "A browser file that imports one ships a secret to the client". The rule classifies an import only when the import resolves. The root link in node_modules and the `exports` entry together make `import '@gab/writer'` resolve.

If we remove the root devDependency or the `exports` block, `@gab/writer` no longer resolves from `src/`. The boundaries refusal then goes silent, and an import of the writer from browser code passes lint. The commit fixed exactly this hole. So the "unused" dependency and export are load-bearing for the security lint, and the removal is not safe.

For @gab/worker alone, the `exports` entry is not load-bearing today, because the root does not list it. That is a different finding, and it is probably a gap in the guard, not dead code.
